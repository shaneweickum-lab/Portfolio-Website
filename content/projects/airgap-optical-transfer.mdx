## Why I built this

I wanted a project that couldn't be mistaken for a tutorial. Most
portfolio projects are variations on the same handful of shapes — a CRUD
app, a dashboard, a chatbot wrapper. I went looking for a problem
unconventional enough that solving it well would say something about how
I think, not just what frameworks I know: air-gapped file transfer,
using nothing but a screen and a camera, with no network at all.

The technique itself isn't new — optical and acoustic data-over-air
techniques go back decades in research and niche commercial products.
The point was never to invent the concept. It was to pick a real,
nontrivial systems problem, architect a correct solution to it myself,
and execute that architecture to a standard I'd actually stand behind —
using Claude Code as my implementation partner throughout, the same way
I'd use any serious engineering tool. I made the calls on the erasure
coding strategy, the homography approach, and what "verified" had to
mean before I'd call any of it done; Claude Code did a lot of the
typing, and pushed back or caught bugs often enough that it earned the
trust to keep doing more of it.

## What it is

Two devices, zero network. One device (the sender) flickers a grid of
colors on its screen; another device (the receiver) points a camera at
that screen and reconstructs the original file — no Bluetooth, no Wi-Fi,
no pairing. Purely light.

## Why this is hard

Consumer cameras and screens aren't built to talk to each other. The
camera's clock and the screen's refresh are completely unsynchronized;
auto-exposure and auto-white-balance actively fight against stable color
classification; and there's no return channel at all — the sender has no
idea whether anything it's showing is actually being received. Every part
of this project exists to solve one piece of that problem:

- **Framing & geometry** — the sender's screen is divided into an 8x8
  grid of colored cells plus four corner fiducial markers. The receiver
  locates those markers in its camera frame and solves an exact 4-point
  homography (a hand-rolled linear solve, not a least-squares
  approximation) to correct for the camera not being perfectly
  perpendicular to the screen. A fifth marker, deliberately excluded from
  the homography solve, exists purely to cross-check it — if the solved
  transform doesn't correctly predict where that marker actually is, the
  frame is thrown out rather than trusted.
- **Color robustness** — auto-exposure and white-balance drift over the
  course of a transfer, so the receiver doesn't trust fixed color targets.
  Fixed reference swatches on screen are re-sampled every frame and used
  to calibrate what "each palette color actually looks like right now"
  before classifying anything else.
- **No return channel, so no retransmission** — reliability comes from a
  rateless erasure code (a GF(2) linear fountain code) instead. The file
  is split into blocks; the sender loops through them and then keeps
  generating random linear combinations indefinitely. The receiver
  accumulates whatever it manages to capture — order doesn't matter, and
  neither does the exact set of drops — and solves for the original file
  with incremental Gauss-Jordan elimination the moment it has enough
  independent equations. A block can be fully recovered mid-transfer, long
  before the whole file is done.
- **Debounce over trust** — a single camera frame captured mid-transition
  between two symbols is a real failure mode (rolling shutter, timing
  jitter). Rather than trust any single frame, the receiver requires two
  consecutive frames to decode to *identical* content before accepting a
  symbol at all.

## Current scope

Optical only, for now — the same core pipeline (fountain code, framing,
one-way broadcast) is designed to extend to an ultrasound channel
(speaker → microphone) later, without redesigning the erasure coding
layer. Realistic throughput is small-file territory (text, keys, small
images) — that's a property of the physical channel, not a shortcoming of
the approach.

## Honest limitation

The full pipeline — real file upload, real canvas rendering, real
browser pixel capture, real fiducial detection, homography, color
classification, debounce, CRC, and fountain decode — has been verified
end-to-end in an actual browser, reconstructing files exactly, including
a case recovered entirely from repair symbols with zero systematic
symbols captured. What hasn't been verified yet is a real camera and a
real screen in an uncontrolled room: actual lighting, hand tremor, and
real webcam auto-exposure behavior are the remaining open risk. The
receiver's live diagnostics (markers found, alignment status,
reprojection error) exist specifically to make that failure mode visible
rather than silent, whenever it's tried on real hardware.
